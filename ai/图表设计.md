## Jinja2 的优势

Jinja2 适合你们现有系统，主要优势是：

1. **服务端渲染简单稳定**  
   不需要复杂前端框架，Python 后端直接生成 HTML，适合内网运维系统。

2. **模板继承能力强**  
   可以做统一布局：

   ```text
   base.html
   ├── dashboard.html
   ├── storage_groups.html
   └── volume_detail.html
   ```

3. **组件复用方便**  
   可以用 `include` / `macro` 复用卡片、表格、状态标签、图表容器。

4. **和 Flask / Python 生态结合自然**  
   如果你们后端已经是 Python，Jinja2 维护成本低。

5. **适合公司内网限制环境**  
   不依赖大量 npm 包，不需要复杂构建链。

Jinja 官方也把它定义为快速、表达力强、可扩展的模板引擎，通过模板加数据渲染最终文档。([jinja.palletsprojects.com](https://jinja.palletsprojects.com/en/stable/intro/?utm_source=openai))

# `design-skill.md`

你可以把下面内容保存成：

```text
design-skill.md
```

然后交给 Agent / Copilot 使用。

```markdown
# Storage Operations Dashboard Design Skill

## Purpose

You are designing and modifying an internal enterprise operations information center for z/OS storage capacity monitoring.

The system focuses only on:

- Storage Group usage
- Volume usage
- Total capacity
- Used capacity
- Free capacity
- Usage percentage
- Historical trend
- Growth trend

The UI should feel like a commercial-grade operations dashboard inspired by Grafana-style dashboard design, but implemented in the existing company stack.

The current application uses server-side rendering with Jinja2 templates. Prefer improving the existing Jinja2-based pages instead of introducing a large SPA framework unless explicitly requested.

---

## Design Goals

The dashboard must answer these questions quickly:

1. Which Storage Groups are close to capacity risk?
2. Which Volumes are close to capacity risk?
3. Which Region / Environment has the highest storage pressure?
4. How has usage changed over time?
5. Which Storage Groups or Volumes are growing fastest?
6. Is the current situation normal, warning, or critical?

Keep the UI simple, dense, readable, and operationally useful.

Do not create decorative charts that do not help operations staff make decisions.

---

## Recommended Information Architecture

Use this page structure:

```text
/overview
/storage-groups
/storage-groups/<storage_group_id>
/volumes
/volumes/<volume_id>
```

If the existing system already has different routes, adapt to the existing routes.

---

## Global Filters

Every main dashboard page should have a compact filter bar near the top.

Required filters:

- Region
- Environment
  - prod
  - dev
  - test
  - sandbox
- System or Sysplex
- LPAR
- Storage Group
- Time range

Recommended time ranges:

- Last 7 days
- Last 30 days
- Last 90 days
- Last 180 days
- Last 1 year

The filter bar should be visually stable and consistent across pages.

Example layout:

```text
[Region ▼] [Environment ▼] [System ▼] [LPAR ▼] [Storage Group ▼] [Last 30 days ▼] [Refresh]
```

---

## Visual Design Style

Use an enterprise dark or neutral light theme.

Preferred style:

- Clean card-based layout
- Subtle borders
- Muted background
- Strong but not excessive status colors
- Dense tables
- Clear typography
- Minimal animation
- No playful or consumer-style visuals

Recommended color semantics:

```text
Normal   : green
Notice   : blue or neutral
Warning  : amber / orange
Critical : red
Unknown  : gray
```

Usage threshold rules:

```text
0% - 69.99%    Normal
70% - 84.99%   Notice
85% - 94.99%   Warning
95% - 100%     Critical
```

Use these thresholds consistently in:

- summary cards
- table badges
- progress bars
- charts
- detail pages

---

## Layout Pattern

Use a top-down dashboard story:

```text
1. Page title and last collection time
2. Global filters
3. Summary KPI cards
4. Main trend charts
5. Risk ranking charts
6. Detailed table
```

This order is important. Do not place detailed tables before summary and trend information unless the page is specifically a list page.

---

## Overview Page

The overview page should show the overall health of storage capacity.

Required KPI cards:

1. Total Capacity
2. Used Capacity
3. Free Capacity
4. Average Usage %
5. Critical Storage Groups
6. Critical Volumes
7. Fastest Growing Storage Group
8. Last Collection Time

KPI card design:

- Large primary value
- Small label
- Optional delta from previous period
- Status indicator color
- Avoid too much text

Example:

```text
┌────────────────────────┐
│ Total Capacity         │
│ 128.4 TB               │
│ +2.1 TB last 30 days   │
└────────────────────────┘
```

---

## Storage Group List Page

The Storage Group list page is one of the most important operational pages.

Required columns:

- Status
- Region
- Environment
- System
- LPAR
- Storage Group
- Total GB
- Used GB
- Free GB
- Used %
- 7-day Growth
- 30-day Growth
- Trend
- Last Collection Time

The table must support:

- Sorting by Used %
- Sorting by 30-day Growth
- Sorting by Free GB
- Filtering by Region
- Filtering by Environment
- Filtering by Status
- Text search by Storage Group name

Preferred visual treatment:

- Used % should be shown as both number and compact progress bar.
- Status should be a colored pill.
- Trend should be a small sparkline if chart library supports it.
- Critical rows should be visually noticeable but not overwhelming.

Do not use full red row backgrounds. Prefer:

- red left border
- red badge
- red progress bar
- subtle tinted background only if needed

---

## Volume List Page

The Volume list page should be similar to the Storage Group list page.

Required columns:

- Status
- Region
- Environment
- System
- LPAR
- Storage Group
- Volume
- Total GB
- Used GB
- Free GB
- Used %
- 7-day Growth
- 30-day Growth
- Trend
- Last Collection Time

The Volume list should make it easy to identify:

- full or nearly full volumes
- volumes growing quickly
- volumes belonging to risky Storage Groups

---

## Storage Group Detail Page

The Storage Group detail page should answer:

```text
What is happening to this Storage Group over time?
```

Required sections:

1. Header
   - Storage Group name
   - Region
   - Environment
   - System
   - LPAR
   - Current status
   - Last collection time

2. KPI cards
   - Total GB
   - Used GB
   - Free GB
   - Used %
   - 7-day Growth
   - 30-day Growth
   - Estimated Days Remaining, if available

3. Trend chart
   - Used GB over time
   - Free GB over time
   - Used % over time

4. Volume table
   - List all volumes under this Storage Group
   - Sort by Used %
   - Highlight Warning and Critical volumes

5. Recent snapshots
   - Optional table of recent collection records

---

## Volume Detail Page

The Volume detail page should answer:

```text
Is this Volume at risk, and how quickly is it changing?
```

Required sections:

1. Header
   - Volume name
   - Storage Group
   - Region
   - Environment
   - System
   - LPAR
   - Current status

2. KPI cards
   - Total GB
   - Used GB
   - Free GB
   - Used %
   - 7-day Growth
   - 30-day Growth

3. Trend chart
   - Used GB over time
   - Used % over time

4. Context
   - Link back to parent Storage Group
   - Show whether the parent Storage Group is also in warning or critical state

---

## Chart Design

Use a small number of highly useful charts.

Recommended charts:

1. Capacity Trend
   - Type: line chart or area chart
   - Series:
     - Used GB
     - Free GB
     - Total GB
   - X-axis: date/time
   - Y-axis: GB or TB

2. Usage Percentage Trend
   - Type: line chart
   - Series:
     - Used %
   - Add threshold lines at:
     - 70%
     - 85%
     - 95%

3. Top Risk Storage Groups
   - Type: horizontal bar chart
   - Metric: Used %
   - Sort descending
   - Limit to Top 10

4. Fastest Growing Storage Groups
   - Type: horizontal bar chart
   - Metric: 30-day Growth GB
   - Sort descending
   - Limit to Top 10

5. Region / Environment Comparison
   - Type: grouped bar chart or compact table
   - Metrics:
     - Total GB
     - Used GB
     - Used %

Avoid using too many pie charts. Pie charts are not recommended for operational capacity analysis unless showing one simple composition.

---

## Chart Styling Rules

For capacity charts:

- Used capacity: blue
- Free capacity: green or gray
- Total capacity: muted gray
- Warning threshold: orange
- Critical threshold: red

For trend charts:

- Prefer clean lines
- Avoid excessive grid lines
- Show units clearly
- Use tooltips if chart library supports them
- Always label axes
- Use GB or TB consistently

For charts with percentages:

- Y-axis should normally be from 0 to 100
- Show threshold markers where possible
- Use threshold colors consistently

---

## Data Formatting Rules

Capacity formatting:

```text
< 1024 GB  => show as GB
>= 1024 GB => show as TB
```

Examples:

```text
850 GB
1.2 TB
12.8 TB
```

Percent formatting:

```text
83.42 => 83.4%
95.01 => 95.0%
```

Growth formatting:

```text
+120 GB
+1.4 TB
-80 GB
```

Date/time formatting:

```text
YYYY-MM-DD HH:mm
```

Always show the timezone if the system supports multiple regions.

---

## Status Calculation

Use this logic consistently:

```python
def usage_status(used_percent):
    if used_percent is None:
        return "unknown"
    if used_percent >= 95:
        return "critical"
    if used_percent >= 85:
        return "warning"
    if used_percent >= 70:
        return "notice"
    return "normal"
```

Do not implement different thresholds in different pages.

---

## Jinja2 Template Guidance

Use Jinja2 inheritance.

Recommended structure:

```text
templates/
  base.html
  layout/
    header.html
    sidebar.html
    filter_bar.html
  components/
    kpi_card.html
    status_badge.html
    usage_bar.html
    chart_panel.html
    data_table.html
  storage/
    overview.html
    storage_groups.html
    storage_group_detail.html
    volumes.html
    volume_detail.html
```

Use macros for reusable UI pieces.

Recommended macros:

```text
status_badge(status)
usage_bar(percent, status)
kpi_card(title, value, subtitle, status)
capacity_value(value_gb)
trend_delta(value_gb)
```

Example macro behavior:

- `status_badge("critical")` renders a red badge.
- `usage_bar(92.1, "warning")` renders an orange progress bar and percentage.
- `capacity_value(1536)` renders `1.5 TB`.

Do not duplicate badge, card, and progress bar HTML across pages.

Prefer a single shared stylesheet for the operations dashboard.

Recommended class naming style:

```text

.ops-header
.ops-filter-bar
.ops-grid
.ops-card
.ops-card-title
.ops-card-value
.ops-card-subtitle
.ops-panel

.ops-panel-body
.ops-table
.ops-status
.ops-status-normal
.ops-status-notice
.ops-status-warning
.ops-status-critical
.ops-usage-bar
```

Keep CSS practical and maintainable.

Do not use excessive gradients, glassmorphism, neon colors, or heavy shadows.

A subtle design is preferred:

- soft borders
- clear spacing
- consistent card heights
- compact tables
- readable font sizes

---

## Table Design

Tables should be dense but readable.

Rules:

- Sticky header if supported
- Right-align numeric columns
- Left-align names and identifiers
- Use compact padding
- Use zebra rows only if it improves readability
- Show empty state if no data
- Show loading state if data is loaded asynchronously
- Keep column labels short but clear

Important columns such as Used % and Status should be visually scannable.

Example row style:

```text
[Warning] US-EAST | PROD | SYS1 | LPARA | SGDB01 | 12.0 TB | 10.8 TB | 1.2 TB | 90.0% | +500 GB | ▁▂▃▅▆
```

---

## Empty State

For pages with no data, do not show a blank page.

Show:

```text
No storage data found for the selected filters.
Try changing Region, Environment, or Time Range.
```

---

## Error State

For data collection or backend errors, show a clear message:

```text
Storage data could not be loaded.
Last successful collection: YYYY-MM-DD HH:mm
Reason: <short error message>
```

Do not expose sensitive backend details.

---

## Refresh and Collection Time

Always show:

- Current selected time range
- Last successful collection time
- Optional next scheduled collection time

Example:

```text
Last collected: 2026-10-15 08:30 UTC
Time range: Last 30 days
```

Do not auto-refresh too frequently. Storage capacity data usually does not need second-level refresh.

Recommended refresh intervals:

```text
Manual refresh
15 minutes
1 hour
Daily
```

---

## Interaction Rules

Click behavior:

- Clicking a Storage Group opens Storage Group Detail.
- Clicking a Volume opens Volume Detail.
- Clicking a critical count card opens a filtered list of critical items.
- Clicking a Top 10 bar opens the relevant detail page or filtered list.

Do not create dead visual elements. If something looks clickable, make it clickable.

---

## Dashboard Copywriting

Use short operational labels.

Good labels:

```text
Used %
Free
30d Growth
Critical SGs
Last Collected
Projected Remaining
```

Avoid long labels:

```text
The percentage of total capacity that is currently used
```

Use tooltips or small descriptions for explanations.

---

## Accessibility

Minimum requirements:

- Do not rely on color only; also show text status.
- Provide readable contrast.
- Use clear focus states for links and buttons.
- Tables should have semantic headers.
- Important numbers should not be image-only.

## Implementation Priority

When making changes, follow this order:

1. Improve layout and navigation consistency.
2. Add or refine KPI cards.
3. Improve status badges and usage bars.
4. Improve Storage Group list table.
5. Add trend charts.
6. Add detail pages.
7. Add advanced interactions only after the basic pages are clear.

Do not overbuild the first version.

---

## What Not To Do

Do not:

- Introduce unapproved external dependencies.
- Use external CDN assets unless the company allows it.
- Build a complex SPA if the existing Jinja2 system can satisfy the requirement.
- Create too many charts on one page.
- Use inconsistent thresholds.
- Hide important capacity numbers behind charts only.
- Use chart colors that conflict with status colors.
- Make production and non-production data visually indistinguishable.
- Show raw backend errors to end users.
- Auto-refresh every few seconds.
- Use decorative animations that distract from operations work.

---

## Agent Instruction

When modifying code:

1. Inspect the existing template structure first.
2. Reuse existing CSS, layout, and components where possible.
3. If components do not exist, create reusable Jinja2 macros.
4. Keep all pages visually consistent.
5. Keep storage capacity semantics consistent.
6. Prefer simple, maintainable code over clever implementations.
7. Do not change backend data shape unless necessary.
8. If backend changes are needed, document the expected fields clearly.
9. Preserve existing authentication and authorization behavior.
10. Make the UI useful for operations staff first, visually polished second.

---

## Success Criteria

The result is successful if an operations user can answer the following within 10 seconds:

1. Are any Storage Groups critical?
2. Are any Volumes critical?
3. Which Storage Group is using the most capacity?
4. Which Storage Group is growing fastest?
5. How has capacity changed over the selected time range?
6. When was the data last collected?
```
