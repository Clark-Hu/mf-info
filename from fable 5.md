Below is a practical, field-tested migration plan for converting from CA 1 (Broadcom, r15) to IBM DFSMSrmm on z/OS 3.1. The good news is this is a well-trodden path — IBM supplies conversion tooling and documentation specifically for CA 1, so you don't have to invent the process. The bad news is that with a large-scale logical tape environment (TS7700 or similar VTS), the risk profile is dominated by retention-policy mapping errors, so the plan below emphasizes validation and parallel running.

## 0. Key reference material (get these first)

Your two core documents are the IBM Redbook _Converting to DFSMSrmm from CA-1_ (SG24-6241), which is written for people planning to convert from CA-1 to DFSMSrmm and covers all aspects from early planning through implementation and customization into production[[2]](https://www.oreilly.com/library/view/converting-to-dfsmsrmm/0738498653/), and IBM's _Data Extraction Programs User's Guide for Conversion to DFSMSrmm_. One important logistical point: beginning with z/OS V2R1, some DFSMSrmm samples and modules used by the conversion instructions were removed from SYS1.SAMPLIB and SYS1.LINKLIB, so you must obtain the conversion parts separately and load them into a PDS source library on the z/OS system where the conversion will take place[[3]](https://www.ibm.com/downloads/documents/us-en/10a99803f3afd80a). The extract program sources (e.g., EDGCSVDS, EDGC5BIN, EDGC5LDR, EDGCRFMT for TMS/CA-1) are downloaded from the web, while EDGCNVT, EDGCEBIN and EDGCVOVL are the supplied conversion programs[[8]](https://docplayer.net/151611455-Data-extraction-programs-user-s-guide-for-conversion-to-dfsmsrmm-version-2-release-1.html). Also engage IBM (and ideally a services partner who has done CA 1 conversions) early — the supplied samples are general, and knowledge of your installation's policies is the key to success; in some instances you may need to modify the sample programs to achieve the required results[[8]](https://docplayer.net/151611455-Data-extraction-programs-user-s-guide-for-conversion-to-dfsmsrmm-version-2-release-1.html).

## Phase 1 — Planning and assessment (4–8 weeks)

**Inventory the current environment.** Document TMC size, active/scratch volume counts (physical and logical), DSNB counts, multivolume/multi-dataset chains, scratch pool definitions, and all CA 1 PARMLIB options (TMOOPTxx). The Redbook contains mapping tables for CA-1 user exits and equivalent DFSMSrmm functions, CA-1 PARMLIB options and DFSMSrmm equivalences, and CA-1 pattern masks and DFSMSrmm equivalences[[1]](https://www.redbooks.ibm.com/redbooks/pdfs/sg246241.pdf) — use these as your gap-analysis worksheets.

**Catalog every interface into CA 1.** This is where commercial systems that have run "for many years" get burned. Identify: user exits (TMSUX2x etc.), any in-house or vendor programs that read the TMC directly (these all break and must be rewritten against the RMM CDS extract or API), DFSMShsm and other External Data Managers, backup products (FDR, DFSMSdss), schedulers, vaulting/offsite processes (CA 1 Vault Management / VPD), DR runbooks, operator automation that traps CA 1 messages, and all reports users depend on.

**Map retention and vaulting policy.** Analyze the RDS retention rules, special EXPDT conventions (catalog control 99000, permanent retention, cycle control), and vault pattern descriptions, and design the equivalent RMM Vital Record Specifications (VRSs), storage locations, and EDGUX100 exit logic. IBM supplies EDGCVRSX as a sample of EDGUX100[[3]](https://www.ibm.com/downloads/documents/us-en/10a99803f3afd80a) specifically to honor converted retention rules; note also that the data extraction programs convert installation-defined tape management policies (retention and outcode location movement) stored in the RDS and VPDD[[3]](https://www.ibm.com/downloads/documents/us-en/10a99803f3afd80a), but treat that output as a starting draft to be reviewed, not a finished product.

**Plan security and skills.** RMM security is SAF/RACF-based (STGADMIN.EDG.* FACILITY profiles, TAPEVOL/TAPEDSN decisions, the TPRACF option), which is structurally different from CA 1's approach — plan the RACF work and train storage admins and operators on RMM ISPF dialogs, TSO RMM subcommands, and new messages. On z/OS 3.1, DFSMSrmm is delivered with the OS; you enable it via IFAPRDxx rather than installing a separate product.

## Phase 2 — Build the RMM environment (in parallel, 4–6 weeks)

Set up RMM without disturbing CA 1: define the DFRMM subsystem in IEFSSNxx, create the started procedure, build the EDGRMMxx PARMLIB member, and allocate and protect the CDS and journal. Given your large logical-volume scale, size the CDS generously and define it as extended-format/extended-addressability VSAM, and plan CDS placement, sharing (GRSRNLxx if shared across a plex), backup, and journal management from day one. Define VLPOOLs to mirror your CA 1 scratch pools — and note a real constraint here: DFSMSrmm pools must be on 10, 100, 1000 boundaries and have no overlap; conversion processing attempts to resolve overlaps but issues warnings when it cannot, and overlaps must be solved by moving volumes to different scratch pool ranges or by using rack numbers[[3]](https://www.ibm.com/downloads/documents/us-en/10a99803f3afd80a). The EDGRCSCR exec converts scratch pool information from the CA-1 parmlib[[3]](https://www.ibm.com/downloads/documents/us-en/10a99803f3afd80a) to help with this. Also build the SMS ACS/PRE-ACS integration if you use pool routing today, and prepare the OAM library exits (CBRUXENT/CBRUXCUA/CBRUXEJC/CBRUXVNL) since your TS7700/ATL currently uses the CA 1-supplied versions — these get swapped at cutover.

## Phase 3 — Trial conversion (repeat until clean)

First clean up the TMC: run TMSPTRS and related utilities to fix chain errors, orphaned DSNBs, and stale entries — broken multivolume chains are a classic conversion blocker. Then run the three-phase conversion: extract, convert, load. The data extraction jobs create sequential output data sets that become input to the EDGCNVT program, and EDGCNVT's output is used to build the DFSMSrmm CDS[[3]](https://www.ibm.com/downloads/documents/us-en/10a99803f3afd80a). In IBM's terms, EDGCNVT together with EDGCVOVL and EDGCEBIN accomplish the Convert Phase; the Postprocessing Phase loads the VSAM KSDS, adds the CDS control record, and cross-checks the records to verify completeness and accuracy, with the control record addition and verification done by EDGUTIL[[6]](https://docplayer.net/amp/153860488-Data-extraction-programs-user-s-guide-for-conversion-to-dfsmsrmm-version-2-release-2-ibm.html). Run EDGUTIL VERIFY(ALL) and drive discrepancies to zero across iterations.

Then validate the result functionally, not just structurally: compare volume counts by status and location between CA 1 and RMM, run a trial VRSEL (EDGHSKP with VERIFY) and compare the RMM scratch-candidate list against CA 1's expiration forecast. Any volume RMM wants to scratch that CA 1 would retain is a retention-mapping defect — this comparison is your single most important quality gate.

## Phase 4 — Parallel run (recommended: 1–3 months minimum)

RMM supports running modes (manual, record, warning, protect) precisely to de-risk this. Run RMM in **record mode** alongside CA 1: CA 1 remains the authority for validation and scratch decisions while RMM records all tape activity into its CDS. The conversion package includes exit modifications and parallel running exits with a defined activation procedure[[3]](https://www.ibm.com/downloads/documents/us-en/10a99803f3afd80a), and the Redbook methodology explicitly covers catalog synchronization, validating DFSMSrmm operation, comparing results, and keeping databases synchronized[[2]](https://www.oreilly.com/library/view/converting-to-dfsmsrmm/0738498653/). During this period, run RMM housekeeping (VRSEL/EXPROC in trial fashion) daily and reconcile scratch lists, vault movement lists, and inventory reports against CA 1's output every day. Cover at least one full business cycle — month-end, and ideally quarter-end — because retention bugs often only surface for periodic workloads. In parallel, rebuild your reporting (RMM Report Generator / EDGRPTD / extract-based reports) and vault picking/movement processes, and rehearse a DR restore using RMM.

## Phase 5 — Cutover

Schedule a tape-quiet window (batch freeze). Take final CA 1 backups, run the final extract/convert/load so the CDS reflects the exact final state, synchronize catalogs (CATSYNCH), and run EDGUTIL VERIFY one last time. Switch RMM to **warning mode** briefly (mismatches produce messages rather than failures), then to **protect mode**. Remove CA 1's intercepts and its subsystem entry from IEFSSNxx (effective at next IPL), swap in the RMM OAM exits for your system-managed libraries, and cut operators over to RMM procedures. Keep CA 1 installed but dormant, with the final TMC preserved, as your fallback: if a severe problem emerges within the fallback window, you can reactivate CA 1 and re-apply the delta of tape activity. Note for planning purposes that a reverse path exists (Broadcom documents an RMM-to-CA 1 conversion), but treat fallback-by-reconversion as a last resort — the practical fallback is reactivating CA 1 within days of cutover.

## Phase 6 — Post-migration stabilization

Automate daily EDGHSKP housekeeping (VRSEL, EXPROC, DSTORE for vault movement, RPTEXT, and CDS BACKUP with journal clear), monitor journal utilization closely (a full journal halts tape recording — automate the backup/clear cycle), update DR documentation and test it, and only decommission CA 1 and terminate the license after an agreed stabilization period (commonly 3–6 months, and aligned with your Broadcom contract dates — contract renewal deadlines should drive your project schedule backwards, with contingency).

## Major risks and things you must be aware of

- **Premature scratching / data loss from retention mapping errors.** This is the number-one risk. Mitigate with the trial VRSEL comparisons, a long parallel run, conservative EDGRMMxx settings during early production (VRSRETAIN, VRSMIN limits, VRSDROP controls), and holding EXPROC in confirm-style operation until confidence is high.
- **Data that does not convert.** The Redbook documents categories of data unavailable for conversion and data not converted[[1]](https://www.redbooks.ibm.com/redbooks/pdfs/sg246241.pdf) — review these tables against every field your operations and audits actually depend on (e.g., usage history, audit trails; the CA 1 Audit data set history does not come across).
- **Logical volume scale (TS7700/VTS).** Verify CDS sizing and conversion runtimes with production-size trial data; note the conversion tooling has specific handling for stacked volumes and exported logical volumes, including setting a default owner for stacked volumes in EDGCNVT[[6]](https://docplayer.net/amp/153860488-Data-extraction-programs-user-s-guide-for-conversion-to-dfsmsrmm-version-2-release-2-ibm.html). Also confirm DEVSUPxx scratch category codes and library partitioning remain consistent through cutover.
- **DFSMShsm and other EDM-owned tapes.** Ensure HSM tapes convert with correct handling (typically permanent EXPDT plus HSM remaining the expiration authority) so RMM never scratches an HSM-owned volume out from under HSM.
- **Anything that reads the TMC directly breaks.** In-house programs, vendor reporting tools, vault interfaces, and automation must be identified in Phase 1 and re-pointed at RMM extracts, the RMM API, or Report Generator output.
- **Scratch pool boundary/overlap restrictions** (10/100/1000 boundaries, no overlaps) may force pool redesign that ripples into ACS routines and operator procedures — surface this early.
- **TMC integrity issues** (broken multivolume chains, orphan DSNBs, duplicate/foreign volsers) block clean conversion — clean up before the first trial extract, and freeze "loan" and manual-status practices during the parallel period so the two databases stay reconcilable.
- **Security model change.** RMM's SAF-based model (STGADMIN.EDG.* profiles, TAPEVOL/TAPEDSN choices) needs deliberate design and testing; don't discover access failures in the cutover window.
- **Operational readiness.** New messages, new ISPF dialogs, new scratch/mount handling, and a new journal-full failure mode — train operators and update automation message tables before cutover, not after.
- **Maintenance currency.** The conversion documentation reflects the current maintenance level of RMM, and you should ensure the documentation level matches the level of the conversion programs you are using[[8]](https://docplayer.net/151611455-Data-extraction-programs-user-s-guide-for-conversion-to-dfsmsrmm-version-2-release-1.html) — bring RMM and the conversion parts fully up to current PTF levels before the first trial.

A realistic end-to-end timeline for a large, long-lived commercial environment is roughly 6–12 months, with the parallel run being the longest single phase.
